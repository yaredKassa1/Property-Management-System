4.5.4 Database Design

The WDUPMS database is designed using a relational data model implemented in PostgreSQL to ensure structured data organization, efficient access, and strong integrity enforcement. The design supports all core property management processes, workflow automation, and comprehensive audit tracking.


DATABASE SCHEMA OVERVIEW

The database consists of 11 primary entities organized into four functional groups:


1. User and Authentication
----------------------------
Users Table
- Primary Key: id (UUID)
- Attributes: username, email, password (hashed), firstName, middleName, lastName, phoneNumber, role, workUnit, wing, college, school, department, administrativeUnit, isActive, lastLogin
- Roles: administrator, vice_president, property_officer, approval_authority, purchase_department, quality_assurance, staff
- Organizational Structure: Supports both academic wing (college/school/department) and administrative wing (unit)


2. Asset Management
--------------------
Assets Table
- Primary Key: id (UUID)
- Attributes: assetId, name, category, serialNumber, value, purchaseDate, location, workUnit, status, condition, assignedTo (FK), description, warrantyExpiry, tagNumber, itemCategory, sourceType, donorName, quantity, createdBy (FK)
- Categories: fixed, fixed_consumable
- Status: available, assigned, in_transfer, under_maintenance, disposed, pending_qa
- Condition: excellent, good, fair, poor, damaged
- Source Types: purchased, donation, transferred
- Foreign Keys: assignedTo → Users(id), createdBy → Users(id)


3. Workflow and Transactions
-----------------------------
Requests Table
- Primary Key: id (UUID)
- Attributes: requestType, assetId (FK), itemName, quantity, estimatedCost, status, priority, requestedBy (FK), workUnit, approvalAuthorityId (FK), approvedBy (FK), purpose, justification, specifications, approvalNotes, permittedAmount, rejectionReason, requesterSignature, approverSignature, completerSignature, completedBy (FK), requestDate, reviewDate, approvalDate, completionDate
- Request Types: withdrawal, purchase, transfer, maintenance, disposal
- Status: pending, under_review, approved, rejected, in_progress, procurement_in_progress, purchased, delivered, item_ready, completed, cancelled
- Priority: low, medium, high, urgent
- Fulfillment Path: direct (from inventory), procurement (new purchase)
- Foreign Keys: assetId → Assets(id), requestedBy → Users(id), approvalAuthorityId → Users(id), approvedBy → Users(id), completedBy → Users(id)

Transfers Table
- Primary Key: id (UUID)
- Attributes: assetId (FK), fromUserId (FK), toUserId (FK), fromLocation, toLocation, fromWorkUnit, toWorkUnit, status, requestedBy (FK), approvedBy (FK), reason, notes, requestDate, approvalDate, completionDate, rejectionReason, transferorSignature, recipientSignature, propertyOfficerSignature, completedBy (FK)
- Status: pending, approved, rejected, in_transit, completed, cancelled
- Three-party signature support: transferor, recipient, property officer
- Foreign Keys: assetId → Assets(id), fromUserId → Users(id), toUserId → Users(id), requestedBy → Users(id), approvedBy → Users(id), completedBy → Users(id)

Returns Table
- Primary Key: id (UUID)
- Attributes: assetId (FK), returnedBy (FK), receivedBy (FK), inspectedBy (FK), status, returnCondition, reason, inspectionNotes, damageDescription, returnDate, receivedDate, inspectionDate, completionDate
- Status: pending, received, under_inspection, approved, rejected, completed
- Condition Assessment: excellent, good, fair, poor, damaged
- Foreign Keys: assetId → Assets(id), returnedBy → Users(id), receivedBy → Users(id), inspectedBy → Users(id)

ProcurementWorkflows Table
- Primary Key: id (UUID)
- Attributes: requestId (FK), currentState, workflowType, approvalAuthorityId (FK), approvalAuthorityDecision, approvalAuthorityComments, approvalAuthorityTimestamp, approvalAuthoritySignature, permittedAmount, vpId (FK), vpDecision, vpComments, vpTimestamp, vpSignature, propertyOfficerId (FK), propertyOfficerTimestamp, purchaseDepartmentNotifiedAt, itemProcuredAt, procurementDetails, qaInspectorId (FK), qaDecision, qaComments, qaTimestamp, completedAt
- Workflow Types: existing_asset (AA → PO → Completed), new_item (AA → VP → PO → Purchase → QA → Completed)
- States: pending_approval, pending_vp_approval, pending_property_officer, purchase_notification_sent, pending_qa_inspection, qa_approved, qa_rejected, item_ready, completed, rejected
- Foreign Keys: requestId → Requests(id), approvalAuthorityId → Users(id), vpId → Users(id), propertyOfficerId → Users(id), qaInspectorId → Users(id)

ProcurementInspections Table
- Primary Key: id (UUID)
- Attributes: requestId (FK), assetId (FK), status, inspectedBy (FK), inspectionDate, assessedCondition, remarks, rejectionReason, correctionRequired
- Status: pending, approved, rejected, needs_correction
- Foreign Keys: requestId → Requests(id), assetId → Assets(id), inspectedBy → Users(id)


4. Audit and Notifications
---------------------------
AuditLogs Table
- Primary Key: id (UUID)
- Attributes: userId (FK), action, entityType, entityId, details (JSONB), ipAddress, userAgent, status, errorMessage, timestamp
- Tracks all system actions with comprehensive metadata
- Foreign Key: userId → Users(id)

TransferHistory Table
- Primary Key: id (UUID)
- Attributes: transferId (FK), action, performedBy (FK), previousStatus, newStatus, notes, metadata (JSONB), ipAddress, userAgent, createdAt
- Actions: created, approved, rejected, completed, cancelled
- Foreign Keys: transferId → Transfers(id), performedBy → Users(id)

Notifications Table
- Primary Key: id (UUID)
- Attributes: userId (FK), title, message, type, isRead, relatedId
- Types: request, return, transfer, general
- Foreign Key: userId → Users(id)


ENTITY RELATIONSHIPS

One-to-Many Relationships:
- Users → Assets (one user can be assigned multiple assets)
- Users → Requests (one user can create multiple requests)
- Users → Transfers (one user can initiate multiple transfers)
- Users → Returns (one user can return multiple assets)
- Assets → Transfers (one asset can have multiple transfer records)
- Assets → Returns (one asset can have multiple return records)
- Transfers → TransferHistory (one transfer has multiple history entries)

One-to-One Relationships:
- Requests → ProcurementWorkflows (one request has one workflow)

Many-to-One Relationships:
- Multiple requests can be approved by one approval authority
- Multiple transfers can be completed by one property officer
- Multiple inspections can be performed by one QA officer


DATA INTEGRITY CONSTRAINTS

Primary Keys: UUID type for all primary keys ensuring global uniqueness

Foreign Keys: Enforced with appropriate cascade rules:
- ON UPDATE CASCADE: Propagate updates to related records
- ON DELETE RESTRICT: Prevent deletion of referenced records
- ON DELETE SET NULL: Allow deletion but nullify references
- ON DELETE CASCADE: Delete related records (for history tables)

Unique Constraints:
- Users: username, email
- Assets: assetId, serialNumber, tagNumber

Check Constraints:
- Asset value ≥ 0
- Request quantity ≥ 1
- Valid enum values for status, role, category fields

Not Null Constraints: Applied to essential fields (username, email, assetId, requestType, etc.)

Indexes: Created on frequently queried fields:
- Users: role, isActive
- Assets: status, category, workUnit, assignedTo
- Requests: status, requestType, priority, requestedBy, workUnit
- Transfers: status, toUserId, fromUserId, assetId
- Returns: status, returnedBy, assetId
- AuditLogs: userId, action, entityType, timestamp


DATABASE CONFIGURATION

Connection Pooling:
- Maximum connections: 5
- Minimum connections: 0
- Acquire timeout: 30 seconds
- Idle timeout: 10 seconds

ORM: Sequelize 6.35.2 for database abstraction and query building

Timestamps: Automatic createdAt and updatedAt fields for all tables (except AuditLogs)

Data Types:
- UUID for primary and foreign keys
- VARCHAR for text fields with length constraints
- TEXT for long-form content
- ENUM for predefined value sets
- DECIMAL for monetary values
- DATE/DATEONLY for temporal data
- BOOLEAN for flags
- JSONB for flexible metadata storage


This database design ensures data consistency, supports complex workflows, enables comprehensive audit trails, and provides a foundation for scalable system growth.
