4.5 SOFTWARE ARCHITECTURE

4.5.1 Overview

This section presents the software architecture for the Woldia University Property Management System (WDUPMS). The architecture is designed to meet functional and non-functional requirements including scalability, security, maintainability, and performance.

The WDUPMS adopts a modular three-tier architectural pattern separating concerns across presentation (Next.js/React), application (Node.js/Express API), and data (PostgreSQL) layers. The system is implemented as a distributed web-based application enabling centralized property management with multi-department access. The modular architecture promotes loose coupling and high cohesion, facilitating independent development, testing, and maintenance.


4.5.2 Subsystem Decomposition

The WDUPMS is decomposed into nine (9) functionally cohesive subsystems, each encapsulating specific business capabilities with well-defined interfaces. This decomposition follows object-oriented design principles to minimize inter-module dependencies while maximizing internal coherence.


1. User Management Subsystem

Purpose: Manages user accounts, authentication, authorization, and role-based access control.

Key Responsibilities:
- User authentication (login/logout) using JWT tokens
- Role assignment and permission enforcement (7 roles: Administrator, Vice President, Property Officer, Approval Authority, Purchase Department, Quality Assurance, Staff)
- Password management and security
- User profile management

Main Components: authController, userController, auth middleware, roleCheck middleware, User model

Cohesion: High | Coupling: Low


2. Asset Management Subsystem

Purpose: Manages the complete lifecycle of university assets from registration to disposal.

Key Responsibilities:
- Asset registration with auto-generated tag numbers (WDU prefix for purchased, donor initials for donations)
- Asset categorization (fixed, fixed_consumable) and status tracking (available, assigned, in_transfer, under_maintenance, disposed, pending_qa)
- Condition assessment (excellent, good, fair, poor, damaged)
- Inventory availability checking and statistics

Main Components: assetController, Asset model, inventoryService

Cohesion: High | Coupling: Low


3. Request Management Subsystem

Purpose: Handles all types of property requests including withdrawal, purchase, transfer, maintenance, and disposal.

Key Responsibilities:
- Request submission with type classification (withdrawal, purchase, transfer, maintenance, disposal)
- Priority management (low, medium, high, urgent)
- Inventory availability checking and fulfillment path determination (direct vs. procurement)
- Request approval/rejection workflow coordination
- Digital signature collection (requester, approver, completer)

Main Components: requestController, requestService, Request model

Cohesion: High | Coupling: Medium


4. Procurement Workflow Subsystem

Purpose: Orchestrates multi-stage approval workflows for procurement requests following university policies (Model 19, Model 20, Model 22 forms).

Key Responsibilities:
- Workflow state machine management with two types:
  * existing_asset: Approval Authority → Property Officer → Completed
  * new_item: Approval Authority → Vice President → Property Officer → Purchase Dept → QA Inspection → Item Ready → Completed
- Approval routing and digital signature collection
- Permitted amount tracking and validation
- State transition enforcement

Main Components: workflowService, ProcurementWorkflow model, approvalHandlers

Cohesion: High | Coupling: Medium


5. Transfer Management Subsystem

Purpose: Manages asset transfers between users, departments, and locations with approval workflows.

Key Responsibilities:
- Transfer request initiation with three-party signature collection (transferor, recipient, property officer)
- Transfer approval workflow: Recipient Approval → Property Officer Completion
- Asset status and location updates during transfer
- Complete transfer history tracking with audit trail

Main Components: transferController, Transfer model, TransferHistory model

Cohesion: High | Coupling: Low


6. Return Management Subsystem

Purpose: Handles asset returns with inspection and condition assessment workflows.

Key Responsibilities:
- Return request submission and receipt by property officer
- QA inspection and condition assessment (excellent, good, fair, poor, damaged)
- Damage documentation and return approval/rejection
- Asset status restoration and unassignment

Workflow: pending → received → under_inspection → approved/rejected → completed

Main Components: returnController, Return model

Cohesion: High | Coupling: Low


7. Quality Assurance Subsystem

Purpose: Manages quality inspection for procured items and returned assets.

Key Responsibilities:
- Procurement inspection with result submission (approve, reject, needs_correction)
- Condition assessment and rejection reason documentation
- Asset status updates based on QA results
- QA inspector assignment and tracking

Main Components: procurementInspectionController, ProcurementInspection model

Cohesion: High | Coupling: Low


8. Notification and Audit Subsystem

Purpose: Provides system-wide notification delivery and comprehensive audit logging.

Key Responsibilities:
- In-app and email notification delivery with role-based routing
- Audit log creation for all system actions with IP address and user agent tracking
- Scheduled reminder management using node-cron
- Notification read/unread tracking

Main Components: notificationController, notificationService, auditLogController, emailService, scheduler

Cohesion: High | Coupling: Low (cross-cutting concern)


9. Reporting and Dashboard Subsystem

Purpose: Generates analytical reports and provides real-time system statistics.

Key Responsibilities:
- Dashboard statistics aggregation (total assets, assignments, transfers, requests)
- Report generation: asset status, transfer history, inventory by category/condition/location, audit trail
- Custom report generation with filters and date ranges

Main Components: dashboardController, reportController

Cohesion: High | Coupling: Low (read-only)

4.5.4 Design Principles Applied

Loose Coupling: Subsystems communicate through REST APIs with JWT-based stateless authentication. Service layer abstracts business logic, and database access is handled through Sequelize ORM.

High Cohesion: Each subsystem encapsulates a single business domain with related functions grouped together, following the Single Responsibility Principle.

Modularity: Independent deployment of frontend and backend with clear interface contracts. Middleware handles cross-cutting concerns (authentication, logging, validation).

Scalability: Stateless API design supports horizontal scaling with database connection pooling and rate limiting.

Security: JWT authentication, role-based access control (7 roles), bcrypt password hashing, Helmet.js security headers, CORS configuration, and comprehensive audit logging.
